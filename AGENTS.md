# ОБЯЗАТЕЛЬНЫЕ ПРАВИЛА РАБОТЫ / AGENTS.md

**Владелец проекта определяет задачу и границы. Эти правила действуют во всех ветках.**

1. НЕЛЬЗЯ самовольно менять работающее поведение, архитектуру, Bluetooth/Wi-Fi протоколы, UUID, подпись APK, package name, AndroidManifest, разрешения, настройки, зависимости, прошивки и способы запуска. **«Делай» означает только ранее сформулированную задачу, не разрешение переделать проект.**
2. Перед правкой зафиксировать проверенный рабочий эталон: ветка/коммит, название версии, контрольные суммы бинарников. Если эталон не определён — не выдавать догадки за факты.
3. Менять только файлы и функции, действительно необходимые для прямо запрошенного изменения. Любые изменения вне области задачи требуют отдельного конкретного разрешения владельца ДО правки.
4. Рабочую версию никогда не перезаписывать. Работать в отдельной ветке; делать минимальные патчи и сравнивать diff с эталоном до сборки. Исходные APK и прошивки сохранять.
5. **Каждая новая функция — отдельная проверяемая правка:** сначала доказать неизменность существующих функций, далее проверить новую. Для APK обязательно проверить байтовый diff/изменённые элементы архива, корректность DEX, подпись, совместимость сертификата для обновления, неизменность пары телефон–очки и разрешений.
6. Тестировать самостоятельно всё, что возможно: сборка, статический анализ, автоматические тесты, протокол и ошибки. Не утверждать «работает на устройствах» без реальных испытаний/логов. Не выдавать неподписанный, недособранный или непроверенный APK за готовый.
7. Запрещено подменять заявку «сделай X» предложениями иных фреймворков, источников маршрутов, устройств, сторонних сервисов или другим приложением без явного разрешения.
8. Если обнаружен технический блокер — показать доказательство и статус, не обходить его путём замены утверждённого решения.
9. GitHub CI `CHANGE-SCOPE-GUARD` сверяет изменённые файлы с `.github/APPROVED_CHANGE_SCOPE.txt` из **базового коммита**, поэтому PR не может сам расширить область доступа к коду. Для новой задачи владелец сначала отдельно утверждает точные пути.
10. Не удалять и не ослаблять `AGENTS.md`, `.github/workflows/change-scope-guard.yml` или контроль изменений по собственной инициативе. Обязательна письменная команда владельца.

**Граница технической защиты:** CI не способен запретить прямой push в main сам по себе. В GitHub Settings → Branches/Rulesets требуется включить защиту main, обязательный успешный чек `CHANGE-SCOPE-GUARD / approved-scope`, PR и проверку владельцем. Пока это не включено, защита обнаруживает нарушения, но не блокирует прямой push.

**Ответственность:** запрет самостоятельных изменений действует всегда — даже если механическая CI-проверка не запустилась.
